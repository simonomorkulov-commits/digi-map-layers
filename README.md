# DiGi · управление картографическими слоями

Тестовое задание на React 19, TypeScript и **vedro 1.1.0**. Три независимых слоя: температура, ветер и инсоляция. Включение запускает mock API; доступны opacity, статусы `loading / success / error` и повторная загрузка после ошибки.

**[Открыть работающий сайт](https://simonomorkulov-commits.github.io/digi-map-layers/)** — GitHub Pages, без установки и регистрации.

## Запуск

Нужен Node.js 24 LTS и npm. Lockfile включён в репозиторий.

```bash
npm ci
npm run dev
```

Откройте адрес, показанный Vite, обычно `http://127.0.0.1:5173`.

```bash
npm run check       # ESLint → Prettier → тесты → TypeScript + production build
npm run test:watch  # тесты в режиме разработки
npm run build
npm run preview
```

## Проверка вручную

1. Включите температуру: `idle → loading → success`, данные появятся на схематичной карте.
2. Измените opacity: карта обновится без нового запроса. `0%` означает полностью невидимый слой, `100%` — непрозрачный.
3. Включите ветер: **его первая попытка предсказуемо завершается ошибкой** через 1,4 секунды. Нажмите «Повторить загрузку» — следующая попытка успешна.
4. Быстро выключите и включите слой во время загрузки. Состояние определяется только последним актуальным запросом.
5. Включите несколько слоёв: запросы и их статусы независимы.

Opacity сохраняется при выключении. Регулировать её можно и до включения. Выключение отменяет запрос, очищает результат и возвращает `idle`; повторное включение всегда загружает заново. Повторная попытка доступна только для включённого слоя в `error`; повторный клик во время загрузки игнорируется.

Карта — собственный SVG-предпросмотр для демонстрации opacity и видимости. Это **схема**, без настоящей GIS-привязки, тайлов или спутниковых данных. Настоящий картографический движок не требовался в задании.

## Архитектура

```text
src/
  layers/
    types.ts             Типы сущностей и discriminated union состояния загрузки
    catalog.ts           Описания слоёв, отдельно от изменяемого состояния
    mockApi.ts           AbortSignal-aware mock с воспроизводимой ошибкой
    controller.ts        Асинхронность, отмена, защита от гонок, команды
    store.tsx            vedro, React-подписки и жизненный цикл контроллера
    controller.test.ts   Проверки гонок и команд с управляемыми Promise
    store.test.tsx       Реальные vedro + React, StrictMode, 120 подписчиков
  components/
    LayerCard.tsx        Универсальная карточка слоя
    MapPreview.tsx       Изолированная подписка каждого SVG-наложения
  App.tsx                Композиция интерфейса
```

Состояние нормализовано как `Record<LayerId, LayerState>`: идентификатор слоя — **ключ верхнего уровня vedro**. Карточка и её наложение подписаны только на свой ключ. Описания слоёв неизменяемы и находятся в каталоге. При обновлении создаётся новый объект только для изменяемого слоя; неизменившиеся значения сохраняют ссылки. No-op изменение opacity не вызывает dispatch.

`createVedro` создаёт Provider и доступ к настоящему store; состояние и уведомления принадлежат vedro. Контроллер обращается к нему через небольшой `StatePort` (`read / update`). Это позволяет отдельно тестировать асинхронные сценарии и заменить mock реальным API без изменений UI. Стабильный Context содержит только команды, поэтому изменения данных не вызывают обновление всего дерева через Context.

### Почему отдельный React-адаптер

Проверены README, типы и исходники [npm-пакета vedro](https://www.npmjs.com/package/vedro), а именно `lib/hooks/useStoreSelector.hook.js`. В версии 1.1.0 штатный `useSelector` подписывается на `@state` и использует `JSON.stringify` для сравнения результатов каждой подписки. Поэтому даже изменение одного слоя заставляет запускаться селекторы остальных слоёв.

`useLayerState` использует публичные методы **vedro** `store.on(id, callback)` и `store.get(id)` с React `useSyncExternalStore`. Подписка адресная; snapshot — стабильная ссылка на сущность. Адаптер корректно переподписывается при смене id и совместим с StrictMode. Это осознанная интеграция vedro с React 19, а не замена vedro другим хранилищем.

### Асинхронность и race conditions

Для каждого слоя контроллер хранит текущий `AbortController` в `Map`. Новый запрос сначала инвалидирует и отменяет предыдущий. При выключении или размонтировании pending-запросы тоже отменяются.

Отмена экономит ресурсы, но сама по себе не гарантирует корректность. Перед записью успеха или ошибки контроллер проверяет **идентичность текущего запроса** и включённость слоя. Даже если API проигнорирует `AbortSignal`, ответ старого запроса не может изменить состояние. `finally` старого запроса также не удалит запись нового. Асинхронный результат обновляет последнее состояние слоя, поэтому изменение opacity во время загрузки сохраняется.

`LoadState` — discriminated union: данные существуют только при `success`, сообщение — только при `error`. Нет `any` в коде приложения; включены `strict`, `noUncheckedIndexedAccess` и `exactOptionalPropertyTypes`. Зависимость vedro содержит собственные старые типы с `any`; приложение их не копирует.

### Масштабирование

Для новых слоёв добавляются записи каталога с уникальными id и реализация их загрузки. Карточка, контроллер и адресные подписки остаются общими. Каталог и API фиксированы на время жизни Provider; при полной замене каталога Provider следует перемонтировать с новым `key`.

Тест на **120 слоёв** проверяет, что обновление opacity первого не перерисовывает остальные 119. Это проверка React-изоляции, а не нагрузочный benchmark: сам vedro 1.1.0 копирует верхний уровень состояния для внутренних уведомлений, поэтому полную стоимость dispatch нельзя назвать O(1). Карточка и её наложение обновляются при изменении своего слоя; дальнейшее разделение подписок по полям стоит делать по результатам профилирования.

Для тысяч строк следующим шагом будет виртуализация списка; для массового одновременного включения — очередь с ограничением запросов. Для больших GIS-данных store следует хранить метаданные и ссылки, а геометрию/тайлы — в картографическом движке или отдельном кеше. В текущем задании эти дополнительные механизмы не нужны.

## Тестирование

Vitest + Testing Library проверяют отмену, устаревшие успехи и ошибки, оба порядка ответов при off/on, очистку `finally`, сохранение opacity во время загрузки, независимые запросы, retry, границы opacity, размонтирование в StrictMode и изоляцию 120 подписчиков. Интеграционный тест проходит путь `loading → error → retry → success` через реальные элементы UI и mock API.

GitHub Actions запускает `npm run check` для push и pull request.

После успешных проверок push в `main` автоматически публикует `dist` на GitHub Pages. Сборка Vite использует base `/digi-map-layers/`, локальный режим разработки — `/`. В настройках репозитория Pages выбран источник GitHub Actions.
